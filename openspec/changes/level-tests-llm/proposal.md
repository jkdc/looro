# Proposal: level-tests-llm

## Intent

Weekly level-verification tests **generated by an LLM** on the backend:
a structured exam model per level (A1–B1, EN/ES), a versioned prompt, a
three-gate validation pipeline (deterministic validator → LLM judge → human
review), K composed variants per week so different users get different
questions, separate endpoints (`generated` LLM-only with 404, `hybrid` with
deterministic fallback) alongside the untouched `current`, and a weekly cron.
Provider/model/API-key configurable from the admin panel and `.env`, with
keys **encrypted at rest** (AES-256-GCM).

Design and decisions: `informe-tests-llm-semanales-2026-10-08.md` (rev. 2,
§1 decisions closed by Joaquín).

## Problem

The deterministic rotation reuses the harvested pool cyclically; there is no
path to new content without an app release, and B2/C1 have no pools at all.
The owner wants fresh weekly tests — generated, validated, stored server-side
— with variety across users and no growing anti-repetition cost.

## Approach

- **Exam models** (`shared/leveltests/exam-models.json`, authored, exported
  into the server bundle): per level, pool targets (2× the exam), section
  mix, passage word ranges, can-do anchor, forbidden patterns.
- **Prompt v1**: system + user (template + 6 few-shot harvested items of the
  level + weekly theme + pool sizes). `prompt_version` stored per week.
- **Three gates**: (1) deterministic TS validator (schema, single correct
  answer among options, passage ranges, reading/listening disjoint, in-
  generation dedupe, language heuristics, section minimums) with one directed
  retry per section; (2) **LLM judge** with a versioned rubric emitting
  per-item `ok|flagged|reject` — `LEVELTEST_VERIFY=flag` annotates the draft,
  `strict` removes rejects and retries flagged sections; (3) human approval
  when `publish_mode=review` (default), auto-approval when `auto`.
- **Variants**: the validated pool composes K=3 exams with the same stable-
  hash block rotation (variant index in the hash) — reproducible, ~50%
  expected overlap between variants, reading/listening disjoint per variant.
- **Storage**: `level_test_weeks` (unique per language+level+week, immutable
  once approved, status draft/approved/retired, generator/model/prompt/
  judge versions, token counts, review verdicts). Served by the new
  endpoints; the deterministic `current` endpoint is untouched.
- **Providers**: single OpenAI-compatible transport with presets
  (`openai`, `glm` z.ai, `opencode` gateway), model list per preset,
  provider config rows with AES-256-GCM-encrypted API keys (master key only
  in env), resolution DB-active → env, and admin endpoints to manage/test
  them. Keys are never returned by the API.
- **Cron**: CLI `npm run leveltests-generate` (Option A, host timer; the
  idempotency lives in the unique week constraint).

## Out of scope (this change)

- Admin panel web UI for the config (backend admin endpoints + CLI are
  included; the panel page is follow-up), app consumption of the new
  endpoints (the bundled composition is identical by golden tests), B2/C1
  and non-EN/ES banks, historical anti-repetition (explicitly declined).
